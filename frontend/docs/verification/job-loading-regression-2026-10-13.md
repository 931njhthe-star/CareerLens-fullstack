# 공고 로딩 및 원복 회귀 점검 — 2026-10-13

## 범위

프론트엔드 저장소만 수정했다. 백엔드 HEAD는 `3863f6eb65775a6483d35ca02b4030c876cfa16c`이며 작업 종료 시 추적·미추적 변경이 없다. 실제 운영 DB의 공고 조회와 화면 이동은 확인했지만, 유료 모델 분석이나 실제 사용자 데이터 변경은 실행하지 않았다.

## 원인과 변경

원본 백엔드의 `/jobs`는 요약 필드만 제공한다. 이전 프론트는 `include_details=true`를 지원하지 않는 응답을 받으면 상세 100건과 회사 정보를 브라우저에서 4개씩 조회한 뒤 목록을 표시했다. 메모리 캐시는 새로고침 시 사라졌다.

- 프론트 서버 `job_catalog_service.py`가 기존 인증 API만 사용해 상세를 최대 16개씩 병렬 조회한다. 회사 조회는 중복을 제거하고 같은 계정의 동시 목록 요청은 합친다.
- 계정별 상세 캐시는 5분, 최대 1,000건이다. 매 요청마다 `/me` 인증과 최신 목록을 확인하며 요약 변경·삭제를 반영한다. 선택한 공고 상세 조회는 기존 API를 통해 새로 읽는다.
- 백엔드 DB 직접 접근, 권한 우회, 샘플 데이터 대체를 하지 않는다. 배포 Docker 이미지에도 새 프론트 모듈을 포함했다.
- 분석 진행 응답의 모든 `message`를 지워 정상 단계 이벤트까지 잃던 오류를 수정했다. 원본 백엔드의 고정 단계 문구만 통과시키며 임의 오류·입력 원문은 계속 차단한다.
- 대시보드·이용 흐름의 일시적 연결 오류를 영구 로그인 차단으로 처리하던 오류를 수정했다. 401/403과 실제 비회원만 로그인으로 안내하고, 일시적 오류는 기존 데이터를 숨긴 후 제한된 재연결을 수행한다.
- 본인 계정 조회를 ‘전체 계정’으로 표시하던 대시보드 문구를 실제 응답 범위에 맞췄다.

## 실제 브라우저 성능

실제 로컬 프론트 5300 + 원본 백엔드 5301 + 실제 공고 데이터, 기존 로그인 계정에서 측정했다. UI 조작 시작부터 공고 상세와 계속 버튼이 표시될 때까지의 벽시계 시간으로 브라우저 도구 오버헤드도 포함한다. 모델 응답 대기 시간을 끼워 넣지 않고 한 번의 도구 실행에서 기다렸다.

| 조건 | 관측 시간 |
| --- | ---: |
| 수정 전 새로고침 | 19.913초 |
| 수정 후 서버 캐시 없는 첫 공고 진입 | 4.110초 |
| 같은 창에서 이력서로 이동 후 공고 재진입 | 0.865초 |
| 수정 후 새로고침 1차 | 8.667초 |
| 수정 후 새로고침 2차 | 2.394초 |
| 수정 후 새로고침 3차 | 2.600초 |
| 5분 캐시 만료 후 재진입 | 4.845초 |

8.667초 표본도 제외하지 않았다. 당시 상세 100건 재조회는 없었으며 해당 지연의 정확한 원인은 확정하지 못했다. 따라서 모든 새로고침이 3초 미만이라는 보장은 하지 않는다. 이후 새로고침에서는 원본 서버 로그에 공고 목록 2회, 선택 상세 1회, 회사 1회만 남아 전체 상세 재조회가 제거된 것을 확인했다. `/auth/session` 404 후 `/me` 200은 기존 인증 방식 자동 탐색이다.

전체 100건/20개씩 페이지 표시, 같은 분류 5건 필터, 선택 공고 제목·본문 표시를 확인했다. 실제 마이페이지·현재 계정 대시보드 접근 및 고정된 이용 흐름 창의 재연결도 확인했다.
