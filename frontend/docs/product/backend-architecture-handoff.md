# 제안된 백엔드 아키텍처와 프론트엔드 연결

검토일: 2026-10-08. 사용자가 제공한 대형 아키텍처 도식과 현재 두 저장소의 구현을 비교한 인계 문서입니다. 도식은 **앞으로 구현할 백엔드 설계안**이며, 아래 내용이 이미 구현되었거나 API 계약으로 확정되었다는 뜻은 아닙니다. 이번 검토로 백엔드 그래프·계산·프롬프트·DB를 변경하지 않았습니다.

기존 폴더와 사용자 흐름을 유지할 수 있습니다. 도식의 평가 에이전트·Global Critic·재평가 노드는 서버 내부 처리 단계입니다. 각 노드에 대응하는 페이지를 추가하거나 사용자를 별도 검증 화면으로 이동시킬 필요는 없습니다.

## 도식에서 확인한 처리 흐름

1. 입력 보안과 사용자 인증을 확인합니다.
2. PostgreSQL에서 이력서·채용공고·기업 참고 자료(Yahoo Finance)를 조회합니다.
3. 문서를 파싱·구조화·정규화하고 입력을 검증합니다. 실패하면 데이터 보완·재파싱을 최대 2회 수행합니다.
4. LangGraph에서 네 평가 에이전트로 병렬 분기합니다. 각 에이전트 내부에서도 세 하위 항목을 병렬로 평가합니다.
5. 항목에 따라 근거 검색, 구조화 평가, Python 규칙 검사, Self-Consistency, Self-Refine을 적용합니다. 세부 흐름에는 최대 1회의 재평가·보정 경로가 표시되어 있습니다.
6. 축별 근거와 점수를 취합·검증하고 **Python 가중 기하평균**으로 네 축의 점수를 계산합니다.
7. 네 축·12개 항목을 모아 **Global Critic**이 근거·점수·영역 사이의 모순을 검증합니다. 필요한 항목만 재평가하거나, 더 재시도할 수 없으면 검증 미완료 상태를 표시합니다.
8. 최종 통합 점수를 계산하고, 항목별 점수·강점·약점·개선 제안이 담긴 LLM 보고서를 생성한 뒤 PostgreSQL에 저장합니다.

도식에는 네 축을 합치는 최종 통합 점수의 구체적인 식이 없습니다. 프론트엔드가 산술평균이나 다른 식을 임의로 정하지 않습니다. Global Critic의 전체 재시도 한도와 종료 정책도 백엔드 계약에서 별도로 확정해야 합니다.

## 현재 화면과 설계안의 관계

| 대상                  | 현재 구현                                               | 설계안 연결 시 필요한 일                                      |
| --------------------- | ------------------------------------------------------- | ------------------------------------------------------------- |
| 사용자 흐름           | 이력서 → 희망 직무 → DB 공고 선택 → 분석 → 결과         | 페이지와 폴더 구조 유지                                       |
| 네 평가축             | 이력서 완성도·직무 적합도·지원 자격 충족도·실무 경쟁력  | 축 이름은 도식과 일치하므로 유지                              |
| 12개 하위 항목과 비중 | 항목명과 참고 가중치 표시, 눈 모션의 순환 주제에 사용   | 서버의 실제 항목 식별자·결과와 매핑                           |
| 피라미드 네 점수      | 사용자 요청에 따른 무작위 시연 값                       | 백엔드가 산정한 네 축 점수를 받는 경계로 교체                 |
| 실제 기존 서버 점수   | 요구사항 연결 70 + 수행 맥락 20 + 수치 근거 10          | 새 네 축으로 이름만 바꾸어 재사용하지 않음                    |
| 분석 그래프           | 순차 규칙 분석 + 선택적 LLM 코칭·검증·제한 재시도       | 네 축 병렬 평가 및 Global Critic은 백엔드 미구현              |
| 검색·기업 참고 자료   | 로컬 키워드 안내 검색; 일반 PostgreSQL/SQLite 연결 지원 | pgvector 근거 검색·Yahoo Finance 활용은 별도 백엔드 구현 필요 |
| 눈의 선·팝업 게이지   | 시각적 진행률; 실제 최종 응답을 받아야 완료             | 실제 작업별 진행 상태는 서버가 제공할 때만 연결               |
| 결과 열람             | 회원은 보고서, 비회원은 정보 없는 골격과 로그인 안내    | 새 계약에서도 같은 접근 경계 유지                             |

12개 항목과 비중은 [피라미드 안내](score-pyramid.md)에 정리되어 있습니다. 도식의 축별 비중은 현재 참고값과 일치합니다.

- 이력서 완성도: 경험 설명의 구체성 40%, 성과 근거의 명확성 35%, 구성과 가독성 25%
- 직무 적합도: 핵심 기술 일치도 45%, 담당 업무 연관성 40%, 우대 역량 부합도 15%
- 지원 자격 충족도: 관련 경력 충족도 60%, 학력·전공 충족도 25%, 기타 필수조건 충족도 15%
- 실무 경쟁력: 업무 규모·난도 경쟁력 35%, 운영·문제 해결 경쟁력 35%, 역할·책임 수준 경쟁력 30%

## 백엔드가 결정하고 구현할 책임

평가 에이전트의 분기·병렬 실행·프롬프트, 도구 선택, SQL/pgvector 검색, 기업 자료 수집, 근거 검증, 재시도와 Global Critic은 백엔드 책임입니다. 점수 계산과 결측 처리도 백엔드가 수행합니다.

특히 경력 기간·겹치는 경력·직무 관련성, 학력과 전공의 동등성, 공고에 기재되지 않은 조건, 필수조건의 충족·미충족·확인 불가를 화면 코드에서 판단하지 않습니다. 근거 부족이나 미산정 상태를 임의로 0점으로 바꾸지 않습니다. 비교 모집단 자료 없이 실무 경쟁력을 실제 지원자 대비 백분위인 것처럼 표현하지 않습니다.

외부 기업 자료는 출처·조회 시점·적용 범위를 서버가 전달해야 합니다. 기업의 매출이나 규모를 지원자가 직접 이룬 성과의 근거로 바꾸어 표시하지 않습니다. DB 비밀번호, 외부 API 키, 프롬프트 원문 및 내부 평가용 추론 기록은 브라우저에 배포하지 않습니다. 사용자에게 필요한 근거 인용과 판단 요약만 반환합니다.

## 계약 확정 후 프론트엔드에서 바꿀 최소 접점

### 1. 완료 보고서와 네 축 점수의 수신 경계

현재 [API 계약 전달 절차](../api/contract-workflow.md)에 따라 백엔드가 계약 원본을 관리하고, 프론트엔드는 `src/shared/api/openapi.json`과 `contract-lock.json`에 승인된 버전을 고정합니다. 현재 고정 버전은 1.7.1입니다. 도식만으로 새 엔드포인트나 응답 필드 이름을 확정하지 않습니다.

현재 `report-state.js`는 최종 분석 응답의 기존 보고서 형식을 검사하고, `status-radar-data.js`의 `pyramidAxes()`는 `demoScoreModel()`을 통해 시연 값을 받습니다. 실제 네 축 점수가 제공되면 **이 수신·정규화 경계에서** 유효한 서버 값을 읽도록 변경합니다. 피라미드의 기하·색·회전 코드를 계산 엔진으로 바꾸지 않습니다.

계약에 합의해야 하는 정보는 다음과 같습니다. 아래는 필요한 의미의 목록이며 확정된 필드명이나 스키마가 아닙니다.

| 정보                                                                | 필요한 이유                                                       |
| ------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 보고서·분석 실행의 식별자, 입력 이력서 버전과 선택 공고 식별자      | 뒤늦은 응답이나 이전 공고의 결과가 현재 화면에 섞이지 않도록 확인 |
| 계약·평가 기준 버전과 산정 시각                                     | 저장된 보고서의 기준을 식별                                       |
| 네 축의 안정된 식별자, 이름, 점수 범위, 실제 점수 또는 미산정 상태  | 배열 순서나 표시 문구에 의존하지 않고 피라미드에 연결             |
| 축별 세 하위 항목의 식별자, 점수·상태·적용 비중                     | 12개 항목을 올바른 축과 연결                                      |
| 항목별 판단 요약, 이력서·공고 근거와 출처                           | 사용자가 평가 이유를 확인                                         |
| 자격 조건의 충족·미충족·확인 불가, 계산에 포함되지 않은 항목의 처리 | 알 수 없는 상태와 낮은 점수를 구분                                |
| 최종 검증 상태, 검증 미완료 항목과 표시 가능한 경고                 | Global Critic 미통과 결과를 검증 완료로 오인하지 않도록 표시      |
| 요약·강점·약점·개선 제안 및 허용된 참고 자료                        | 기존 보고서 본문에 연결                                           |
| 최종 통합 점수의 제공 여부·계산 기준                                | 네 축에서 프론트엔드가 임의로 종합 점수를 만들지 않도록 제한      |

실제 응답을 받기 전까지 현재 시연 표시를 유지합니다. 새 계약의 응답이 잘못되었거나 일부 값이 비어 있는 경우, 그것을 무작위 실제 평가 결과로 대체하지 않습니다. 구형 보고서와 시연 자료는 새 실제 평가 결과와 구분합니다. 개선 후 예측 점수 역시 서버의 명시적인 근거와 정책 없이 새로 만들지 않습니다.

### 2. 분석 상태와 완료 조건

현재 회원은 `POST /api/v1/analysis`, 비회원은 `POST /api/v1/guest/analysis`로 최종 분석을 요청합니다. 추가 질문 화면은 사용하지 않으며 빈 보완 답변을 전송합니다. `report-loading.js`는 실제 응답과 최소 4초 연출을 모두 기다린 뒤 보고서 전환을 시작합니다.

12개 팝업 주제와 선의 게이지는 현재 **시각적 진행 표시**입니다. 도식의 병렬 에이전트가 실행 중이라는 사실이나 각 항목의 실제 완료율을 나타내지 않습니다. 서버가 항목별 이벤트 또는 작업 상태 조회 계약을 제공하면 그때 연결합니다. 제공되지 않으면 현재 최종 응답 기반 완료 확인을 유지합니다.

실시간 상태 계약을 도입할 때에는 항목 식별자, 대기·실행·재시도·완료·실패 상태, 요청 식별자와 최종 완료 신호를 합의해야 합니다. 재시도와 검증이 끝나기 전에는 프론트엔드 타이머만으로 보고서가 확정되었다고 판단하지 않습니다. **처리 완료**와 **검증 통과**는 별개입니다. 서버가 검증 미완료 상태의 보고서도 반환하기로 결정하면 결과 화면에서 그 상태를 명시해야 합니다.

현재 프론트엔드 Python 프록시는 상위 요청에 60초 제한을 두고 전체 응답을 읽습니다. 장시간 병렬 분석이나 실시간 이벤트가 필요하면 이 통신 방식도 함께 검토해야 합니다. 비동기 작업 조회나 스트리밍 중 어떤 방식을 쓸지는 백엔드와 계약을 확정한 뒤 구현하며, 현 시점에 존재하지 않는 작업 API를 호출하지 않습니다.

### 3. 인증과 비회원 결과 보호

도식의 첫 번째 인증 노드는 기존의 비회원 체험 정책을 변경하라는 지시로 해석하지 않습니다. 현재 비회원은 첨부·공고 선택·분석까지 진행하고, 결과 열람은 로그인·회원가입 후에만 가능합니다. 자세한 현행 정책은 [구현 흐름](implemented-flow.md)을 따릅니다.

새 병렬 분석에서도 비회원 응답·실시간 이벤트에 이력서 본문, 실제 점수, 평가 근거 또는 보고서 내용을 포함하지 않아야 합니다. 비회원 완료 신호는 현재처럼 허용된 메타데이터로 제한합니다. 로그인 안내 뒤에서 실제 보고서를 받아 흐림 처리하는 방식으로 변경하지 않습니다. 만료·파기·계정 변경·화면 이탈 시 늦게 도착한 결과가 표시되지 않도록 기존 보호도 유지합니다.
