# CareerLens 프론트엔드–백엔드 연결 점검

> 이 문서는 2026-10-12 초기 점검 당시의 기록입니다. 같은 날 이후 추가된 공개 대시보드·보고서 삭제·비회원 분석과 표시 방식은 현재 [README](../../README.md), [대시보드 연결 문서](admin-dashboard-handoff.md), [비회원 보고서 연결 문서](guest-report-handoff.md)를 기준으로 확인하세요. 아래의 당시 미지원 항목과 화면 설명이 최신 상태를 뜻하지는 않습니다.

점검일: 2026-10-12 / 작업 범위: 로컬 프론트엔드. 백엔드·환경 파일·DB는 수정하지 않았고 GitHub에 올리지 않았습니다.

## 핵심 원인

실제 분석 결과는 이미 `/api/v1/evaluations/{run_id}/result`에서 받아 아래 점수표에 표시하고 있었습니다. 그러나 위 피라미드는 `status-radar-data.js`에서 모든 보고서를 `demoScoreModel()`에 전달하여 **프론트엔드의 Math.random()이 만든 35~90점**을 사용했습니다. 서버가 무작위 그래프 점수를 반환한 문제가 아닙니다.

현재는 동일한 백엔드 결과를 점수표·피라미드·세부 평가에 연결합니다.

| 백엔드 필드 | 화면 축 | 처리 |
|---|---|---|
| resume_completeness | 이력서 완성도 | 원 점수와 소수점 유지 |
| job_fit | 직무 적합도 | 원 점수와 소수점 유지 |
| qualifications | 지원 자격 충족도 | 그래픽 내부 eligibility 축에 명시적으로 연결 |
| practical_competitiveness | 실무 경쟁력 | 원 점수와 소수점 유지 |
| overall_score | 종합점수 | 별도 백엔드 값 사용, 프론트에서 평균 계산하지 않음 |

예시 `78.8 / 52.6 / null / 65.1`은 `78.8 / 52.6 / 미산정 / 65.1`로 표시합니다. 모든 축이 산정된 경우 기존 입체 도형과 성장 모션을 사용합니다. 미산정 축이 있으면 100점 기준 프레임과 확인된 축의 선·점만 표시하여 누락값으로 꼭짓점이나 면을 만들지 않습니다. 실제 0점은 유효한 값으로 유지합니다.

## 함께 수정한 연결

| 항목 | 기존 문제 | 변경 |
|---|---|---|
| 점수 변화 예시 | 실제 보고서에서도 임의 상승값 표시 | 실제 보고서에서 제거, 명시적 데모만 허용 |
| 평가 기준 | 고정 시연 항목·예정 비중 표시 | 응답의 evaluation_criteria 기준·비중·점수·판정 표시 |
| 평가 제외 | not_applicable을 근거 부족으로 분류 | 평가 제외로 표시하고 보완 필요 목록에서 제외 |
| 개선 제안 | 평가 설명/일반 문구로 대체 | improvement_suggestion을 그대로 사용, 없으면 미제공 안내 |
| 강점·부족 근거 | 강점에 고정 문구 사용 | 해당 criterion의 reasoning_summary 표시 |
| 신뢰도·한계 | 별도 카드에 정보 누락 | confidence, comparison_basis, estimated, validation_status, issues 연결 |
| 근거 출처 | resume/job 영문 또는 임의 기본값 | 이력서/채용공고로 구분, 출처 없으면 정보 없음 |
| 질문 | 프론트에서 임의 후속 질문 생성 | 실제 결과에서는 생성 제거, 기존 요청대로 질문 UI 숨김 유지 |
| 등록 공고 | 로컬 Markdown이 서버 변경사항을 덮음 | 서버 상세·회사 정보 우선, 로컬 자료는 조건에 맞는 직무 분류 보조만 사용 |
| 공고 목록 | 요약 API만 읽어 상세 정보 누락 | `/jobs/{id}`와 `/companies/{id}` 연결, 상세 조회 최대 4개 동시 처리 |
| 누락 근무지 | 근무지 협의로 추정 | 정보 없음 표시 |
| 선택한 공고 | 브라우저 캐시가 옛 내용 유지 | 서버 상세로 갱신, 삭제된 공고는 선택 해제, 권한·서버 오류는 그대로 안내 |
| 보고서 날짜 | 클라이언트 현재 시각 사용 | 서버 보고서 완료→평가 완료→서버 생성 시각 순으로 사용 |
| 준비 상태 | 고정 8/5/2 근거 숫자와 가짜 완료 단계 | 실제 계정에서는 미제공 처리, 과거 캐시도 실제 상태로 재사용하지 않음 |
| 로딩 백분율 | 눈 모션 타이머의 시각적 비율 사용 | 실제 계정은 progress_percent 사용, 미제공이면 확인 중. 최종 보고서 수신 전에는 결과 화면을 열지 않음 |

## 백엔드 API가 아직 없는 항목

아래는 프론트가 기존 API를 놓친 문제가 아니라 현재 백엔드에 기능이 없는 항목입니다. 존재하지 않는 저장을 성공했다고 표시하거나 DB를 직접 수정하지 않습니다.

- **관심 공고 영구 저장, 공고 생성·수정·삭제:** 실제 회원의 버튼과 직접 편집 주소는 연동 대기 상태로 차단했습니다. 명시적 데모의 임시 동작은 유지합니다.
- **분석 보고서 개별·일괄 삭제:** UI는 준비되어 있지만 삭제 API가 없어 비활성 상태입니다.
- **관리자 역할 및 대시보드 데이터:** 현재 `/me`에 관리자 역할이 없고 운영 통계 API도 없습니다. 실제 일반 계정에 버튼이 노출되지 않으며 통계를 임의 숫자로 채우지 않습니다.
- **OAuth·비밀번호 재설정:** 현재 계약에 API가 없습니다.
- **희망직무만으로 실제 분석:** 현재 평가 생성 API는 저장된 resume_id와 job_posting_id를 요구합니다.

다음 입력·화면 범위도 확인했습니다. 회원가입의 이름은 현재 백엔드 가입 계약(email/password)에 없어 서버에 전달되지 않습니다. 희망직무의 ‘특히 살펴보고 싶은 부분’도 브라우저 준비 상태이며 실제 평가 생성 요청의 입력값이 아닙니다. 이 두 항목을 계정 프로필·평가 지시로 사용하려면 백엔드 계약 확장이 필요합니다. 이번 점수 연결 작업에서 백엔드 지원을 새로 구현하지 않았습니다. 또한 이력서 목록 API는 현재 이력서를 불러오는 데 사용하지만 여러 이력서를 선택·관리하는 별도 화면은 아직 없습니다.

## 기존에 연결되어 있거나 의도적으로 사용하지 않는 항목

- 회원가입·로그인·토큰 갱신, 이력서 업로드·조회·삭제, 평가 생성·진행·취소, 결과·저장 보고서 조회는 실제 백엔드 경로를 사용합니다.
- `/evaluations/{id}/events` SSE 대신 `/progress` 폴링을 사용합니다. `/progress`가 404일 때만 기본 평가 상태 조회로 전환하며, 오류를 가짜 성공 결과로 바꾸지 않습니다.
- `/reports/{id}/download`는 백엔드에 있지만 사용자가 내보내기 버튼 제거를 요청하여 화면에 연결하지 않았습니다.
- `/companies/{id}/financials`는 백엔드에 있지만 현재 제품 화면에 기업 재무정보 영역이 없어 사용하지 않습니다. 임의 재무정보도 표시하지 않습니다.
- 로그인 전 공고/이력서 예시와 명시적 데모는 가상 자료입니다. 실제 회원 평가에는 등록된 백엔드 공고 ID가 필요합니다. 디자인 비교실의 임의 값은 실제 보고서와 분리됩니다.

## 주소와 책임

현재 브라우저는 `http://127.0.0.1:5300/api/v1/...`로 요청합니다. 프론트 서버가 이를 `http://127.0.0.1:5301/api/v1/...`의 FastAPI로 전달합니다. Supabase 주소는 데이터 저장·인증 설정이며 이 로컬 FastAPI 주소와 역할이 다릅니다. 다른 컴퓨터의 127.0.0.1은 그 컴퓨터 자신을 가리킵니다.

## 검증 범위

전체 단위 테스트 **501개 통과**. 모든 API를 합성 응답으로 가로챈 브라우저 검증으로 실제 결과 계약의 소수점·0점·null, 세부 판정과 제안, 저장 보고서 재조회, 모바일 폭, 서버 공고 상세 우선 표시·미지원 쓰기 차단·데모 호환을 확인했습니다. 실제 진행률이 모션 타이머에 덮이지 않고, 서버 100%만으로 최종 결과가 열리지 않는 것도 확인했습니다. 실제 유료 분석 실행이나 DB 쓰기는 하지 않았으므로 모델이 점수를 산출하는 품질 자체를 다시 평가한 작업은 아닙니다.

백엔드 기준 커밋은 `57bd0cf866b3c66a853f7c79d7cdace5faffefcf`이며 `origin/develop`과 동일합니다. 작업 종료 시 Git 변경 없음도 확인했습니다. 프론트엔드는 로컬 반영 상태이며 GitHub에 푸시하지 않았습니다.
